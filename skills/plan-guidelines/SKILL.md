## 核心宗旨

将代码设计、重构方案和改动清单，整理成开发者能够快速建立理解、检查并执行的说明。

这里的重点不是把方案压缩成固定模板，也不是尽可能展示更多技术细节，而是帮助用户回答几个实际问题：

- 这次到底要解决什么问题？
- 准备改哪些地方，改动之间有什么关系？
- 每个文件为什么需要改？关键代码会怎么变化？
- 哪些内容不在本次范围内？改完如何确认没有偏离目标？

## 输出倾向

以下是推荐方向，不是必须逐条遵守的固定格式。根据方案的复杂度、用户的上下文和改动类型，可以合并、删减或调整顺序。

### 1. 先让用户看到全貌

通常先用一段简短总结，或列出几条核心改动，让用户先知道方案的结论。总结应关注业务或代码结构上的变化，不要把分析过程全部铺开。

例如：

```text
总结：
1. task_type 继续负责任务执行，不再和 appFeatureCode 或任务名称绑定。
2. 删除原来的任务名称展示推导逻辑。
3. 新增独立的任务名称生成和保存逻辑。
```

如果方案很小，一句话结论可能就足够；如果方案较大，可以按阶段、模块或依赖关系组织总结，不必强行使用编号。

### 2. 按改动组织内容，而不是按分析过程组织内容

优先围绕“要做的改动”展开。每个改动尽量说明：涉及的文件或模块、它在当前流程中的职责、要改变的内容，以及改变后的结果。

不要只给出孤立的文件名、行号或函数名。代码位置是定位辅助，应该结合它负责的事情和本次修改原因一起说明。也不要为了完整而重复用户已经知道的背景。

一个改动可以使用标题、编号、短段落、列表或其他合适的形式。编号有助于执行和沟通，但不是所有方案都需要编号。

### 3. 代码示例服务于理解

当代码对理解改动有帮助时，可以使用 diff、局部代码、伪代码或流程图。选择最能表达变化的形式，不要机械地把所有文件都写成 diff。

适合展示的内容包括：

- 删除或新增的关键接口、字段、函数调用。
- 数据在改动前后的流向。
- 能体现职责变化的核心代码。
- 需要用户确认的行为差异。

与本次方案无关的实现细节可以省略，用简短说明代替。省略时要让用户知道这里确实还有实现，而不是误以为代码只有示例中的几行。

例如：

```diff
- const taskName = getTaskNameByType(task.task_type);
+ const taskName = task.name;
```

```ts
// 只展示任务名称生成的关键流程，具体实现省略
export async function generateTaskName(taskType: string) {
	const content = createTaskNameContent(taskType);
	await saveNameSnapshot(content);
	return generateByTimestamp();
}
```

不要求每个改动都附代码；如果文字、流程图或数据结构更清楚，就使用更合适的表达方式。

### 4. 把“为什么”和“改完后”说清楚

技术动作本身通常不难看懂，难的是判断它解决了什么问题。因此在必要时补充：

- 当前逻辑为什么不合适。
- 这次改动解决了哪个耦合、歧义或维护问题。
- 改动后谁负责什么。
- 对已有数据、旧流程或兼容性的影响。

这些说明应服务于决策和执行，不要扩展成与改动无关的长篇教程。

### 5. 明确范围，但不要过度罗列

在存在边界、兼容策略或风险时，补充“保留什么”“不改什么”“如何验证”。这些内容不是固定必填项，应在确实能帮助用户判断方案时出现。

例如可以说明：

```text
保留：task_type 作为任务执行键。
不再使用：task_type 作为历史任务名称的展示来源。
验证：新任务保存名称；旧任务仍能通过兼容逻辑正常展示。
```

不要为了满足格式而列出大量显而易见的“不涉及内容”，也不要在没有依据时虚构测试结果、行号或实现细节。

## 写作边界

- 面向正在做决定或准备改代码的开发者，而不是面向另一个 AI。
- 结论、改动和影响优先；推理过程只保留能帮助理解或决策的部分。
- 允许根据上下文使用标题、列表、表格、diff、代码片段、流程图等不同形式。
- 不要把本 Skill 中的示例格式当作硬性模板。
- 如果用户已经给出了明确格式或关注点，优先服从用户要求。
- 如果方案仍存在关键不确定性，应单独标出待确认项，而不是用确定语气掩盖它。

1. task_type 继续作为任务执行键，不再承担任务名称展示职责。

文件：task/dbt.ts

```diff
	export async function addTask(taskArgs: AddTaskArgs) {
+   const name = await generateTaskName(taskArgs.taskType);

		return tx.task.create({
			data: {
				task_type: taskArgs.taskType,
+       name,
			},
		});
	}
```

改完后，任务名称在创建时固定下来，后续不会因为 task_type 的映射变化而改变历史任务展示。
